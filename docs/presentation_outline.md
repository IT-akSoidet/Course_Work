# Презентация к защите курсовой

## Слайд 1. Тема и актуальность
- Разрозненное бронирование аудиторий приводит к конфликтам.
- Цель: единый Telegram-канал для прозрачного бронирования.

## Слайд 2. Цели и задачи
- Реализовать роли (`student`, `teacher`, `admin`).
- Исключить двойные бронирования.
- Поддержать импорт расписания занятости.

## Слайд 3. Архитектура решения
- Telegram Bot (`aiogram`) + API (`FastAPI`) + PostgreSQL.
- Слои: handlers -> services -> repositories -> DB.

## Слайд 4. Модель данных
- Таблицы: `users`, `roles`, `rooms`, `bookings`, `room_unavailability`, `audit_logs`.
- Ключевые индексы по `room_id + time`.

## Слайд 5. Механизм защиты от конфликтов
- Транзакция + `SELECT ... FOR UPDATE`.
- Проверка пересечений с активными бронями и расписанием.
- Конфликты уходят в `pending` для админа.

## Слайд 6. Демонстрация сценариев
- Студент: поиск и создание брони.
- Преподаватель: приоритетная заявка.
- Администратор: `/admin_queue`, `/approve`, `/reject`.

## Слайд 7. Тестирование и качество
- Unit-тесты парсинга команд и CSV-импорта.
- Обработка ошибок в API и проверка ролей.

## Слайд 8. Итоги и развитие
- MVP готов для пилота.
- Следующие шаги: интеграция внешнего API расписания и веб-панель.
